# v1.0.95

本版修的是自动化「一单接一单白等 90 秒」的问题：某只采集浏览器**假死**（TCP/HTTP 都应答，但 CDP 命令一个都不回）时，Worker 的探活一直判它正常，于是不恢复、不重启，后续任务继续往这只坏浏览器上撞。

## 修复

- **探活升级：从「HTTP 探活」改为「真 CDP 握手」**
  - 以前只 `GET /json/version`：假死 Chrome 的 DevTools HTTP 线程照常 200，探活永远通过。现在会连上调试 WebSocket 真跑一条 `Browser.getVersion`，收到回应才算可用。
  - 结果分三态：`ok` / `down`（端口没起）/ `wedged`（HTTP 通但不回命令 = 假死）。探活缓存健康 5 秒、不健康 15 秒，健康浏览器一次探活约 40ms。
  - 现场 2026-11-25：15:56–16:27 有 29 单全部卡在 `browserType.connectOverCDP: Timeout 90000ms exceeded`，只打 slot2/slot3 的两只浏览器，且全程同一个 browser id（一次假死后 10/19 单连续撞墙）。前兆是同日的执行器 `0xC0000409` 崩溃、`save-draft executor timed out`，以及 Chrome 子进程的 Crashpad 转储。
- **假死浏览器必须杀掉重起，不能复用**
  - API：`launch_mabang_browser(..., force_restart=True)` 会跳过「看到 `/json/version` 正常就复用」的分支，先 taskkill 再拉起；`POST /api/mabang-browser/auto-login` 新增 `restart: true` 参数承接这个语义。
  - 页面导入期间（`reuse_running_only`）强制忽略 `restart`：操作员正在填的可见窗口绝不动。
- **Worker：报错分类 + 下一单前强制重起**
  - 执行器报 `connectOverCDP` / `0xC0000409` / `Playwright save-draft executor timed out` / `browser_context_missing` 之一，就判定「浏览器这一侧坏了」，给该槽位打 `_browser_restart_pending`，**下一单领取前先杀掉重起**。
  - 重启第一次立即执行，之后退回 60s 冷却（Chrome 起不来时不会每个轮询周期都 taskkill 一次）。
  - 浏览器假死时的等待文案直接写明「端口还应答，但 CDP 命令不再响应；已尝试杀掉重起」，不再只说「无法连接」。
- **执行器连接预算 90s → 25s**
  - 分工改为「执行器快速失败、Worker 换浏览器」：重起后连接通常只要百毫秒级，25s 已覆盖慢页面（历史 34s 慢连接的场景在重起后不复现），又不会让假死浏览器把整轮任务拖死。

## 升级提示

- 无新增依赖；不改数据结构、不改 `data/`、`storage/` 和 `.env`。
- **需要重启 API 与本机 Worker**：`force_restart` 在 API 进程里，`_cdp_health` 在 Worker 进程里，旧进程不会自动用上新代码。执行器是每单新起的 node 子进程，文件更新后即生效。
- 升级过程会重启 API，正在跑的自动化任务会被中断；建议等任务队列空闲时再点更新。
