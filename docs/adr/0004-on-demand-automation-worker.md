# 自动化 Worker 按需启动：平时关闭，有任务才唤醒，空闲 10 分钟自动关闭

现场：三个 Worker 进程和三只采集浏览器是**常驻**的。ADR 0003 引入账号 × 槽位并行后，一个
账号 2 个槽位就是 2 只 Chromium + 2 个 Worker；没有任务时它们照样占内存、占 CDP 端口、
一直握着马帮登录会话，界面上的「运行中」也让人分不清「在干活」还是「只是开着」。

现场要求（2026-10-09）：**自动化 Worker 平时关闭；有任务了再唤醒；执行完 10 分钟没有新任务
就自动关闭。**

## 决策

1. **新增两个设置项**（设置 → 自动化 Worker）：
   - `worker.start_on_demand`（默认开）：按需启动。关掉就回到老行为——API 起来就把 Worker
     拉起来、一直挂着。
   - `worker.idle_shutdown_minutes`（默认 10，`0` = 不自动关闭，上限夹到一天）。
2. **API 启动不再无脑拉 Worker**：按需启动模式下，只有队列里**已经有可领任务**时才顺手唤醒；
   否则等建任务或看护轮（每 15 秒）按需唤醒。重启 API 不会再凭空起进程和浏览器。
3. **唤醒数量按任务数对齐**：某个账号有 N 个可领任务时，最多唤醒
   `min(N, 每账号并行槽位)` 个目标（已在跑的不重复起）。任务在途（`claimed`/`running`，即使
   租约已过期）也算“有活”。建任务那条路径用「本次新建的 ready 任务数」当输入，比读整库更准。
4. **手动停止 = 压制，且跨 API 重启有效**。`/api/worker/stop|pause` 会把压制时间写进该目标的
   `worker-state.json`（`manual_hold_at`）。看护轮不再唤醒被压制的目标；**新建任务**会解除该
   账号的压制（手动停只压旧任务），操作员点「启动/恢复」也会解除（`start()` 清压制）。
   没有这条，「按需唤醒」会把操作员刚停掉的 Worker 立刻拉回来。
5. **空闲关闭的口径**（三者同时满足才算空闲，从最后一单的活动时间算起）：
   - 该账号没有可领任务、也没有在途任务；
   - Worker 最近一次结果里没有 `job_id`（没在执行某一单）；
   - 距「该账号最后一单的活动时间 / 进程启动时间」的最大值已满 N 分钟。
     **不能**拿 Worker 的 idle 心跳时间当锚点：空闲时它每 30 秒重写一条 `idle` 结果，
     `activity_at` 永远是「刚刚」，计时永远不成立（第一版就这么错过一次）。

   满足后 **停进程 + 关掉这个「账号 × 槽位」的采集浏览器**（现场确认要一起关，省内存）。
6. **两件例外不关**：该槽位正在做「从马帮当前页导入」（那只浏览器是操作员的可见窗口）；
   或有一轮**店铺采集**在途（采集用的就是同一只采集浏览器，关掉会把采集断在半路）。
7. **自愈只治 `failed`**：空闲关闭把进程停成 `stopped`（或操作员 `paused`），看护轮不会把它
   复活；只有崩溃（`failed`）才自动重启。这条原本就成立，这里明确写下来，避免以后有人把
   「按需关闭」和「崩溃自愈」写成互相打架。

## 未被推翻的部分

- 登录门禁不变：唤醒目标时仍然先准备采集浏览器并确认马帮登录，失败就不启动、不领任务
  （见 `2026-09-17-worker-login-gate-design.md`）。
- 槽位隔离不变：每个目标一只浏览器 + 一个 Worker（ADR 0003）；空闲关闭是按目标逐个判断的。
- 任务执行期读的是建任务时的快照；空闲关闭只动进程与浏览器，不碰任务数据。
- `worker.auto_start` 仍然是「不可关闭」的兼容字段：它现在的含义是「允许系统自己拉 Worker」，
  而**什么时候拉**由按需启动 + 看护轮决定。

## 代价与风险

- 当天第一次唤醒要现起浏览器 + 自动登录（几秒到几十秒）；这段时间任务仍在 `ready`，不会被
  算作失败。
- 关掉采集浏览器后，操作员点「店铺采集」需要先有那只浏览器（界面上的「启动自动化浏览器」
  或建一个任务都会把它带起来）。采集需要操作员先在窗口里打开目标店铺，这本来就是人工步骤。
- 空闲关闭只保证「不关正在干活的目标」，不保证关得最快：看护轮 15 秒一轮，最坏多留 15 秒。
